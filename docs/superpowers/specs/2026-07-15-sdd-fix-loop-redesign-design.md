# SDD 修复循环重新设计 — 设计规范

**状态：** 已批准的设计（2026-07-15 与 Jesse 头脑风暴）；实施计划待定。
**目标：** 使子代理驱动开发技能的审查-修复循环收敛且自主，并让文档可读，同时不重写其经评估调优的语言。
**硬性约束：** 现有经评估调优的句子只移动位置，不改写措辞。新机制附带演练证据交付。

## 问题

四个，均在实际会话中观察到：

1. **病态审查循环。** 循环字面上就是"重复直到批准"——没有轮次上限。每次复审都是对整个 diff 的全新完整审查，因此非确定性的前沿审查者每轮都会暴露新发现，而非验证修复。结果：实现、审查、修复、审查、审查、修复、审查、修复——没有断路器。严格成本规范（2026-06-10）独立测得审查循环次数是运行间成本方差的最大来源。
2. **矛盾的修复策略。** 流程图和"Constructing Reviewer Prompts"派发专门的修复子代理；Red Flags 说"Implementer（同一子代理）修复它们"；implementer-prompt.md 的"After Review Findings"部分假设实现者会被重新调用。一个技能里对"谁来修复？"有三种答案。
3. **结构堆积。** 十三个顶层章节；一个活动的指导散落在其中四个章节里。"Constructing Reviewer Prompts"是个大杂烩，装着审查者指导、修复策略、最终审查策略和计划冲突裁决。
4. **Red Flags 格式。** 七个同级技能使用 `| Excuse | Reality |` 合理化表格；SDD 却带着 17 条"Never"列表加三个"If X"迷你块。

## 设计决策

| # | 决策 | 理由 |
|---|----------|-----------|
| 1 | 原实现者修复自己的审查发现——原地恢复它。 | 它已持有任务上下文；所有权胜过顺路修补者。全新的"修复子代理"为每个发现重建上下文，且缺乏任务框架。 |
| 2 | 复审范围限定于发现项。 | 每轮全新完整审查是搅动引擎。限定范围的复审使循环在结构上收敛；最终全分支审查仍是广泛的安全网。 |
| 3 | 断路器设在五轮修复：三次恢复，然后两次在更强模型上的全新派发。 | Jesse 的决定。一个挺过三次恢复的循环通常意味着实现者看不到自己的问题——全新的强能力派发一举完成去锚定和能力提升。 |
| 4 | 触发时，控制器裁决并路由。不新增人工检查点——结构性失败到达现有的 BLOCKED 停止。 | SDD 的要点是自主执行。控制器持有审查者缺乏的计划和跨任务上下文；现有文本已授权它（"在审查循环中裁决它"）却从未指明机制。 |
| 5 | 按生命周期重组 SKILL.md，保留调优句子。 | 从根源修复"难以跟随"。内容移到使用点，符合内部方向（近期提交将回顾章节折叠进使用点）。 |
| 6 | 将 Red Flags 转换为 `| Excuse | Reality |` 合理化表格；硬规则迁至使用点。 | 与其他七个技能一致。借口得到反驳；规则在读者行动处执行。 |

## 修复循环

触发：任务审查返回 spec ❌ 或任何 Critical/Important 发现。

**第 1–3 轮——恢复原实现者。** 逐字发送发现项（Critical/Important 加 spec 缺口）。实现者修复、重跑覆盖测试、将修复报告追加到其现有报告文件，并返回简短契约。在没有代理恢复的 harness 上，"恢复"是携带简报、报告文件和发现项的全新派发——无论哪种方式，报告文件都是持久记忆。

**第 4–5 轮——全新实现者，更强模型。** 完整任务上下文：简报、报告文件、未决发现项，以及框架"先前的实现者已尝试此任务 N 次；现在你拥有该任务。"

**每轮的复审都限定范围。** 复审者收到简报、更新后的报告、原始发现列表，以及修复范围的 diff 包（`review-package FIX_BASE HEAD`，其中 FIX_BASE 是审查者上次审查的 head；脚本已接受任意范围）。它逐项判定每个发现已解决/未解决，并仅标记修复 diff 中的新破坏。修复未触及代码上的新发现报告为非阻塞；控制器将其记入台账供最终审查。

**修复报告完整性门（现有规则，保留）：** 派发复审前，确认修复报告列明覆盖测试、运行的命令和输出。

**不提前退出。** 控制器绝不在上限前裁决——提前退出会重新打开当前内容刻意关闭的"预判发现以省去审查循环"漏洞。一个例外，与今天相同：与计划文本要求冲突的发现立即交给人类（计划权威，而非循环搅动）。

**次要发现**从不进入循环：到达时记入台账（现有规则，保留）。

### 触发时的裁决

第五轮失败后，控制器停止派发，并对照简报、计划和跨任务上下文判断每个未决发现：

- **有争议或错误** → 记入台账并附一行裁决（"controller: reviewer wrong because X"），继续。最终审查看到双方。
- **真实，非承重** → 记为已知未决，继续。后续触及该区域的派发携带指向该条目的指针。
- **真实且承重**（后续任务依赖它，或它揭示计划缺陷）→ 现有 BLOCKED 停止。搁置并继续会将结构性失败推迟到最昂贵的点，并让依赖项在其上构建，因此结构性失败停止运行——通过已存在的停止条件，而非新检查点。

每次裁决都是一条台账条目。静默丢弃仍被禁止。

## 文档重组

新骨架，按执行顺序：

1. 引言——为何用子代理、核心原则、叙述、连续执行
2. 何时使用——不变，包括决策图
3. 流程——为新循环更新图表
4. 设置——worktree、台账检查/恢复、预检计划审查、待办
5. 模型选择——保持为一个横切章节；每次派发都查阅它，因此将其折叠进使用点会重复五次
6. 任务循环——五个编号步骤：
   1. 派发实现者（task-brief 脚本、五部分派发组合、模型行必需）
   2. 处理报告（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）
   3. 审查任务（review-package 脚本、审查者派发组合、约束透镜、不预判、⚠️ 处理）
   4. 修复循环（上述机制）
   5. 完成任务（台账追加、待办更新）
7. 最终审查——包、模型固定、一次修复波、一次限定范围复审、裁决
8. 完成——finishing-a-development-branch
9. 常见合理化——表格
10. 示例工作流——更新以展示基于恢复的修复轮和断路器未触发

"Constructing Reviewer Prompts"、"File Handoffs"和"Durable Progress"消解进各规则适用的步骤。每个经评估调优的句子恰好落在一个新位置；实施计划中的移动映射追踪源 → 目标，以便审查验证没有内容被丢弃或改写。

## 合理化表格

借口形态的 Never 条目转换为行；新行覆盖循环病态。草稿行（最终措辞在实施时确定）：

| 借口 | 现实 |
|--------|---------|
| "spec 合规上够接近了" | 审查者发现缺口 = 未完成。 |
| "我自己修，派发是开销" | 控制器修复污染你的上下文并跳过审查。恢复实现者。 |
| "再来一轮就会收敛" | 超过上限后，轮次不会收敛。裁决。 |
| "审查者反正会找到新东西" | 限定范围的复审检查修复，而非品味。未触及代码上的新发现进入台账，而非循环。 |
| "这个发现明显错误，我丢掉它" | 你只在上限时裁决，且每次裁决都是台账条目。静默丢弃被禁止。 |
| "修复很小，跳过复审" | 未审查的修复正是回归落地的方式。 |

非借口的硬规则（绝不并行实现者、绝不在没有 diff 文件时派发审查者、模型行必需、绝不重新派发台账已完成的任务）迁至其使用点。

## 提示模板

- **implementer-prompt.md**——"After Review Findings"按恢复语义重写：你将带着发现项被恢复；修复、重跑覆盖测试、追加到你的报告文件、返回简短契约。
- **task-reviewer-prompt.md**——仅初始审查；尾部的复审句子移出。
- **re-review-prompt.md（新）**——限定范围的复审契约：输入是简报、更新后的报告、原始发现项、修复范围的 diff 包；输出是逐项发现判定（已解决/未解决）、修复 diff 中的新破坏，以及其外的非阻塞观察。单独模板因为它是不同的契约——重载完整审查模板产生了当前的歧义。
- **接管派发（第 4–5 轮）**——由 implementer-prompt.md 加 SKILL.md 指导组合（简报、报告路径、未决发现项、接管框架）；无新模板文件。

## 最终审查循环

不变：merge-base 包、最强模型、一个修复者带完整发现列表。新增：对修复波恰好一次限定范围复审，然后控制器裁决。残余承重发现浮现在 finishing-a-development-branch，人类已在那里。分支末端也获得有界循环。

## 评估

`evals/` 中三个新演练场景：

1. **恢复，而非重新派发：** 任务审查返回发现项；控制器必须恢复同一实现者，而非派发修复子代理。
2. **断路器触发：** 一个预置的永不满足审查者；控制器必须在第五轮失败后停止派发，裁决、记入台账并继续——而非循环。
3. **结构性发现停止：** 一个承重发现（后续任务依赖它）；控制器必须通过 BLOCKED 停止，而非搁置。

加上现有 SDD 场景的前后运行，以捕捉重组带来的回归。
