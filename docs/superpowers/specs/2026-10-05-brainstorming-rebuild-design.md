# Brainstorming 重建：意图

## 为什么需要它

编码智能体非常擅长构建。它们会按照自己认为人类想要的东西去构建，但很少在动手前充分提问或充分调研。brainstorming 技能的存在就是为了弥合这一差距：在开始构建任何东西之前，把人类真正的意图挖掘出来，包括他们自己还没想清楚的部分。

最初的 superpowers 提示词用大约四十个词就做到了这一点：“我脑子里有个想法。我希望你围绕它问我很多问题。当你认为自己理解了我真正想要的东西时，用大约 200-300 字的段落向我描述。一旦我们对齐了，就写出一份非正式的规格说明。”当前的技能已经增长到约 2,600 词，几乎全部内容都关于路由（spike / 有界 / 架构性）、审批关卡，以及从规格到计划的交接。意图被压缩成了一段话，其默认动作是“就目的问一个聚焦的问题”，而这对人并不奏效。

这是一次从零开始的重写，不是编辑。

## 目标

- 智能体理解任何非平凡事物背后的*为什么*，因为知道为什么的智能体会把上百个未明说的决策做好。
- 人类最终会想清楚自己真正想要什么。好的问题能帮助他们充实一个尚未成形的想法。
- 适用于任何领域：软件、演讲、装修、小生意。
- 最终产出一份文档，该领域中一位有才华的构建者可以据此制定计划，而无需回头再问人类。

## 一次会话应有的感觉

**从私下检查开始。** 智能体问自己：关于他们想要什么以及为什么，我实际知道什么？如果答案是“几乎全部”（“把图标做成矢车菊蓝”），它就确认并继续。如果缺少任何非平凡的信息，它就开始提问。

**一次问一个问题。** 默认使用平实的语言，略高于人类的水平。问题应该帮助人类思考，而不是考他们。

- 先让他们描述。开放式问题胜过菜单，因为菜单会把人们引向智能体的假设。
- 只有当他们卡住时才提供菜单。
- 如果他们说“你猜”或“你觉得呢”，总是给出提议。
- 把问题建立在真实时刻（“带我走一遍上一次……”）和具体权衡（“如果它只能把其中一件事做好……”）之上。
- 询问先例和现状：别处已有什么，现在已有什么。
- 询问*如何做*的哪些部分他们想自己决定，哪些他们更愿意交给构建者。

需要覆盖的范围，大致按顺序：这是什么类型的东西、它特别在哪里、目标、非目标、反目标、他们在意的细节，以及他们想委托出去的部分。这些是领域，不是脚本。智能体从不把它们当作字面问题读出来。

**提供调研。** 一旦有了一些基础，智能体就提出去看看：代码库或项目、人类自己的文件和数据，或者网络。由人类决定是否去看。

**一旦事情变得具体，就展示而非讲述。** 对于图表、模型和一次性原型，使用视觉伴侣，因为看比读更有效。

**用 spike 来感受。** 智能体式开发是瀑布式的，但非常非常快。一次快速的一次性构建往往是弄清人类想要什么或某件事是否可行的最便宜方式，智能体应在有帮助时提出。当人类只想做 spike 时，智能体就让开。Spike 没有测试或只有极少的测试，不是无懈可击的，也不走完整的计划、实现和审查流程。Spike 学到的东西会反馈到对话中。

**在内部广泛思考。** 在提出任何东西之前，智能体生成多个想法并丢弃弱的。只有当比较能帮助人类决策时，它才向人类展示比较。

**复述。** 一旦智能体认为自己理解了，它就用大约 200-300 字的段落描述自己的理解，并在每段之后调整。

## 它产出什么

一份平实的书面文档，涵盖：

- 意图和为什么
- 目标、非目标、反目标
- 约束
- 人类在意的*如何做*的部分，按他们的决定记录
- 明确留给构建者的部分

**完成测试：** 在人类审查之前，一个扮演该领域有才华构建者的全新子智能体阅读文档，并列出它仍然需要问的问题。这些问题回到人类那里。当构建者没有重要问题可问时，文档就完成了。

**确定工作规模。** 一旦意图清晰，智能体把工作归入三种规模之一，大声说出是哪一种，并让人类可以推翻：

- **一个快速、清晰的任务。** 意图从一开始就清晰。确认并执行。
- **一个小改动。** 完整描述存在于聊天中。没有文档文件。
- **一个有书面设计的项目。** 完整描述就是上面的文档，随后是一份完整计划（对于软件，是 writing-plans 技能）。

这就是旧的 spike / 有界 / 架构性选择现在所在的位置：在意图之后，而不是之前，用平实的名称。

**审批。** 无论规模如何，人类在开始构建任何东西之前批准完整描述：小改动在聊天中批准，项目通过阅读文档批准。

**选择退出。** 在会话早期，智能体提一次：如果人类不想走这个流程，直接说就行。

## 非目标

- 设计人类没有要求决定的架构。文档记录人类在意的*如何做*；其余属于构建者。
- 专门针对软件。
- 为琐碎请求走形式。

## 反目标

- 审问：对着人类读一长串问题清单。
- 引导入坑：用引导性菜单把人类引向智能体偏好的想法。
- “你到底想做什么？”这类让人类替智能体思考的问题。
- 小请求膨胀成多阶段项目。
- 在人类同意复述之前就开始构建。

## 决策

- 技能保留名称 `brainstorming`。其他技能和 README 指向它。
- 视觉伴侣及其服务器脚本保持原样。
- `spec-document-reviewer-prompt.md` 被构建者检查提示词取代。
- 智能体在把构建者检查的问题带给人类之前先筛选：它从上下文中回答能回答的，丢弃关于委托细节的问题。没有子智能体工具时，它自己运行检查。
- 保留一个简短的硬性关卡：在人类批准完整描述之前，不构建任何东西。一个例外：人类同意了的 spike。它保持标记为一次性。保留它产出的东西是一个新请求，要走关卡。
- 构建者检查只对书面文档运行。小改动留在聊天中。
- 触发描述保留强烈的“在任何创造性工作之前使用”措辞。开场检查让琐碎请求保持低成本。
- 旧技能中的待办清单示例去掉。编码旧路由的评估（`brainstorming-todo-purpose-discovery`、`brainstorming-todo-shared-intent`）重写以匹配。
- 软件项目保留 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 作为文档的默认位置。

## 留给构建者

- 技能的章节结构和措辞。
- 构建者检查的确切提示词。
- 在没有人类偏好的情况下，非软件文档保存在哪里。
