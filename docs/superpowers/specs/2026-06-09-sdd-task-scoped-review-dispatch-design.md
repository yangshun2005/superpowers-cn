# SDD 任务范围内的审查调度

将 subagent-driven-development 的每任务审查做得更便宜、更快，同时不削弱审查力度：把每任务审查提示词限定在任务范围内，并停止重复工作——而最终分支审查仍保持宽泛。

## 问题

SDD 中的每任务代码质量审查者经常在单任务 diff 上做分支审查规模的工作。来自两个真实本地 SDD 会话的证据：`a1a6719a-6109-453a-9933-34ae396f5bae`（sen-core-v2）和 `0cc1a12d-9984-4c35-8615-9d42dadb2c47`（serf），均位于 `~/.claude/projects/` 下：

- 在 sen-core-v2 会话中，7/8 的质量审查者执行了全仓库 grep；最昂贵的一次在约 200 秒内运行了 50+ 条 Bash 命令。在两个会话中，质量审查者的成本是同一任务上规格审查者的 4-8 倍。
- 规格审查者的提示词包含"只读取此 diff 中的文件。不要爬取更广泛的代码库"，因此保持克制：6-16 次工具调用，14-65 秒。
- 没有审查者自主运行重型测试。观察到的每一次包级或重复测试运行，都是控制器编写的提示词明确要求的（"检查所有使用处"、"如有用则运行测试，尤其是竞态相关的"、"还有其他地方读取 `Meta()` 吗？"）。

根本原因，按影响排序：

1. **每任务质量提示词继承了合并就绪审查。** `code-quality-reviewer-prompt.md` 委托给 `requesting-code-review/code-reviewer.md`，后者询问架构、可扩展性、安全性、生产就绪性，并以"可以合并了吗？"结尾。这种框架为单任务 diff 赋予了分支级广度。规格提示词的 diff 范围守卫从未被继承过来。
2. **控制器没有关于编写审查者提示词的指导**，因此它发明了开放式指令（"检查所有使用处"），审查者会字面执行。
3. **流水线中的重复工作。** 质量模板的"计划对齐"维度重新检查了规格审查者刚刚验证过的内容。审查者在相同代码上重新运行实现者已经运行（并报告，附 TDD 证据）的测试套件。
4. **每任务审查和最终审查共用一个模板**，因此"每任务窄、最终宽"在任何地方都没有体现。

一份现场报告（`~/2026-06-09-code-quality-reviewer-scope-budget-issue.md`）首先指出了这一点。其引用的会话和头条数字无法核实，但其定性诊断已对照两个真实本地会话得到确认。对其的一处更正：横切审计（锁顺序、变更的契约）有时是*正确*的审查方法——修复必须将广度限制在已陈述的具体风险之后，而不是禁止它。

## 目标

- 每任务审查限定在任务范围内：diff 优先阅读、有理由的扩展、无冗余测试运行。
- 最终全分支审查保持当前广度。
- 审查捕获的内容不减少。

## 非目标 / 明确保留

- **完整重审保留。** 当审查者在修复后重审时，它仍以完整阅读广度审查整个任务。（它不会重新运行实现者刚刚在修订代码上运行的测试。）这有意拒绝了现场报告的"重审预算"补救措施：其最差引用示例（一次重审运行 `-race` 和 `-count=100` 循环）的成本由下面的测试预算来遏制，而不是通过缩小重审者的阅读范围。
- ~~**两个审查阶段保持分离。** 规格合规性和代码质量保持为独立的子代理，串行门控。不合并。~~ **被下面的成本迭代取代**：实时评估经济学显示每次调度的开销主导成本，维护者把所有选项都摆上了桌面。每任务阶段现在是一个任务审查者，带两个裁决；独立的宽泛最终审查保留。
- **协调者保留模型判断。** 审查不强制模型层级，两个方向都不。
- **`requesting-code-review/` 不受影响。** 它仍是最终分支审查和临时审查的宽泛模板。
- 裁决顺序（规格合规性先于质量报告）、修复-重审循环，以及修复 Critical/Important 发现的要求，均不变。

## 成本迭代（发布后评估经济学）

一旦质量加固文字（证据规则、约束携带、纯净输出）落地，实时前后运行就暴露出成本回归：go-fractals 从 42.8 分钟 / 14.5M token（第一个任务范围版本）变为 69.9 分钟 / 32.2M（加固版本），同时达到基线同等质量（盲评 8.5 vs 8.5）。按子代理轮次分析将成本归因于，按顺序：廉价模型在多步工作上花费 2-3 倍轮次（1197 个子代理轮次中有 678 个是 haiku）、每次调度开销（每任务 3 次子代理启动，每次重新推导 diff；控制器协调占美元的一半），以及证据规则叙述。

- **迭代 1：** 轮次数胜过 token 价格的模型指导（多步工作的中层级下限）、可选内联 diff、引用而非叙述证据、Important = 修复前不可信任、仅为 Critical/Important 调度修复。结果：68.2 分钟 / 22.9M——token 下降 29%，墙钟时间持平；当措辞为可选时，控制器仅在 22 次审查调度中的 2 次粘贴了 diff。
- **迭代 2：** 每任务规格审查和质量审查合并为一个 `task-reviewer-prompt.md`（一个审查者、一次 diff 阅读、两个裁决；一次修复调度同时处理两类发现）；实现者在迭代时运行聚焦测试，提交前运行一次完整套件。结果（go-fractals）：47.5 分钟 / 15.7M / $13.55——在每个轴上都击败基线，盲评 9/10 vs 基线 7/10。
- **迭代 3：** 校准将阻塞合并的可维护性损害（逐字重复、吞掉的错误、无断言的测试）命名为 Important，Minor 发现必须粘贴到最终审查中以供分诊；审查者的怀疑扩展到实现者的设计理由（"按 YAGNI 保留"是主张，不是裁决）；diff 作为文件交给审查者（`git diff > /tmp/sdd-task-N.diff`，重定向使其永不进入控制器上下文；审查者一次 Read 调用），此前粘贴到提示词的指导未被采纳（11-17 次调度中的 0-6 次），原因是本地合理的上下文经济学。
- **最终冻结配置（e355795），全部五个场景通过：** go-fractals 44.4 分钟 / 13.4M / $11.67（相比基线 -32% 时间、-37% token、-27% 美元）；svelte-todo 62.8 / 19.7M / $15.76（-21% / -28% / -25%）；rejects-extra-features $1.31（vs $1.88）；spec-reviewer-flaws 持平；植入缺陷场景（v3：判断调用的开放标记透明度标准，对名称承诺验证却从不执行的测试的必须修复标准）通过，缺陷被捕获并修复。

### 迭代 4-5（2026-06-10）：方差诚实、结构性修复、正向配方

同配置重跑暴露了运行间方差（相同提示词上 44.4→57.1 分钟；审查者逃生舱口胃口在 1.0→6.3 工具调用/审查之间摆动），因此所有后续声明使用范围。go-fractals 上的五个并行实验变体加上对真实本地会话的记录挖掘（含负面结果的完整日志：`evals/docs/experiments/2026-06-10-sdd-cost-experiments.md`）产生了最终配置：

- **采纳：** 最终审查包（最终审查者在控制器模型价格下 33→6 轮）；两个模板中 REQUIRED `model:` 行（文字指导在会话中途衰减过一次，为 17 次调度继承了 opus，+$5）；任务简报 + 报告文件（`scripts/task-brief`；保真锚点，适度的上下文节省）；`<git-dir>/sdd/progress.md` 中的进度账本（真实会话在压缩后重新调度了整个已完成任务序列——约 22 个任务 269 次调度）；全能最终修复器（真实会话的逐发现修复波成本超过其所有任务）；范围化修复测试；唯一 SHA 范围附带名称（worktree/submodule 安全）；调度组合配方和审查者命名风险预算（微测试：正向配方 3.0 转录值 vs 禁令 4.4 vs 对照 3.6——禁令可能适得其反；见 `2026-06-10-positive-instruction-redesign-design.md`）。
- **测试并拒绝：** 控制器轮次批处理和并行调用流水线（控制器每条消息恰好发出一次工具调用——每次运行中 0 条多工具消息；其 46% 的轮次是思考/叙述，一个提示词免疫的下限）；后台调度流水线（机制在 7/28 中采纳，但在这些场景上收益低于 ±6 分钟噪声下限）。
- **最终验证配置（b81f35b 家族），全部门通过：** go-fractals 54.1-54.7 分钟 / 14.4-16.6M / $12.81-14.31（基线 64.9 / 21.2M / $16.07）；svelte-todo 55.0 分钟 / 19.3M / $14.99（基线 79.7 / 27.3M / $20.98）；植入缺陷通过 / $2.77。在所有 8 次同设计 fractals 运行中：44.4-57.1 分钟 / 13.4-20.0M / $11.67-14.84——最差抽样在每个轴上都击败基线；典型中段节省约 20-25%。

## 设计

### 共享原则：不要在未变更的代码上重新运行测试

实现者的报告包含测试结果和针对审查中确切代码的 TDD RED/GREEN 证据。审查者通过阅读来验证。审查者仅在阅读引发具体疑问且无现有运行可回答时运行测试——且是聚焦测试，不是套件。在审查者子代理为只读的 harness 上（例如 Antigravity 将审查者模板映射到 `research` 类型，该类型无命令访问权限），审查者改为在报告中命名它将运行的测试。

修复后，实现者重新运行覆盖修订代码的测试；重审者不重复该运行。目前没有任何东西强制执行这个前提：`implementer-prompt.md` 仅描述初始实现-测试-提交流程，没有修复迭代指令。因此本规范还向 `implementer-prompt.md` 添加：修复审查发现后，重新运行覆盖修订代码的测试，并将结果包含在修复报告中。

此原则出现在两个审查者提示词、实现者提示词和控制器指导中。

### 1. 新文件：`skills/subagent-driven-development/code-quality-reviewer-prompt.md` 变为自包含

停止委托给 `requesting-code-review/code-reviewer.md`。每任务质量审查者获得自己的范围化提示词模板：

- **框架：** "你正在审查一个任务的实现的代码质量。"一个任务范围的门，不是合并审查。
- **规格合规性已确定：** 规格审查已通过；不要重新争论需求或计划对齐。
- **保留的审查维度：** 代码质量（清晰性、重复、错误处理）、测试质量（真实行为，不是 mock）、可维护性，以及现有的 SDD 特定检查（单一职责、独立可测试性、来自计划的文件结构、此变更贡献的文件增长）。删除：计划对齐、安全/可扩展性/生产就绪维度、合并裁决。
- **范围预算：** 从 `git diff BASE..HEAD` 开始；先读取变更文件；仅为了评估你能命名的具体风险而检查相邻代码。横切变更——锁顺序、变更的函数/API 契约、共享可变状态——是合法的命名风险，证明检查调用点是合理的。默认不要爬取代码库。
- **测试预算：** 上述共享原则，加上：无包级套件、竞态检测器或重复/高计数运行，除非你先命名了具体的疑似 flake 或竞态。否则，在报告中推荐重型验证而不是运行它。实现者报告的测试输出中的警告或噪声是发现——输出应该是纯净的（实现者的自审也检查这一点）。
- **证据规则：** 审查者用 file:line 证据回答每个 What-to-Check 项，而不是裸的 yes/no。（在实时评估运行显示审查者通过了提示词指向的缺陷后添加——一个可访问名称检查和一个临时目录清理检查都得到了无支持的"yes"答案，而缺陷就坐在被审查的 diff 中。）
- **只读规则** 以精简形式保留：不修改工作树、索引、HEAD 或分支状态。当前模板中的 `git worktree add` 操作说明句子不带入此文件——diff 范围审查从不需要检出另一个修订版（与下面规格提示词清理相同的理由）。
- **裁决：** 优点 / 问题（Critical/Important/Minor）/ "任务质量：已批准 | 需要修复。"

### 2. `skills/subagent-driven-development/spec-reviewer-prompt.md` 清理

- 移除 `git worktree add` 操作说明句子。只读规则保留；diff 范围的规格审查从不需要检出另一个修订版。
- 解决仅 diff 守卫与"独立验证一切"之间的张力：规格合规性通过将 diff 与需求对照阅读来判定。实现者的 TDD 证据覆盖"它能运行"——应用共享测试原则。
- 新的第三裁决通道：无法从 diff 验证的需求（位于未变更代码中、跨任务）报告为明确的"⚠️ 无法从 diff 验证——控制器应检查 X"项，而不是要么爬取要么静默通过。流程图的二元通过/失败菱形无法路由此情况，因此控制器指导（§3）定义处理方式：⚠️ 项不阻止调度质量审查者，但控制器必须在标记任务完成前自行解决每一项（它持有计划和跨任务上下文）；控制器确认为真实缺口的项被视为规格审查失败并返回实现者。
- 将虚构前提"实现者完成得可疑地快"替换为有根据的怀疑：将实现者的报告视为关于代码的未验证主张。同样的不信任，没有虚构事实。

### 3. `skills/subagent-driven-development/SKILL.md` 控制器变更

- **模型选择：** 将"架构、设计和审查任务：使用最可用的模型"替换为判断指导——像选择实现者模型一样选择审查者模型，按 diff 的大小、复杂性和风险缩放。"任务复杂性信号"列表被重新界定，以明确其条目描述实现任务；审查者模型选择遵循同样的判断，因此窄 diff 审查不会自动映射到"广泛代码库理解 → 最可用模型"。
- **审查者提示词构建**（Red Flags 附近的新指导）：调度审查者时，不要在没有具体任务特定理由的情况下编写开放式指令（"检查所有使用处"、"如有用则运行竞态测试"）；不要要求审查者重新运行实现者已在相同代码上运行的测试；不要为审查者预判发现（永远不要指示审查者忽略或不标记特定问题——在审查循环中裁决疑似误报）；每任务审查是任务范围的门——宽泛审查在最终全分支审查时进行一次。（预判规则是在一次实时评估运行抓到控制器捏造"计划禁止共享辅助函数"的主张并指示质量审查者不要标记植入的 DRY 违规后添加的。）控制器还必须在其粘贴的需求中包含约束任务的规格/设计全局约束——版本下限、命名和文案规则、平台要求：一次实时运行交付了 `go 1.26.1` 模块下限，违背"Go 1.21+"设计，因为没有审查者看到该约束。控制器还必须在每次调度时明确指定模型——省略的模型继承会话的（通常最昂贵的）模型，这静默地击败了模型选择。
- **处理规格审查者 ⚠️ 项**（新指导，与 Handling Implementer Status 并列）：控制器在标记任务完成前自行解决每个"无法从 diff 验证"项；确认的缺口作为失败的规格审查返回实现者。
- **最终审查保持宽泛，明确地：** 最终全分支审查者调度节点获得指向 `../requesting-code-review/code-reviewer.md` 的明确指针。（目前该模板只能通过每任务质量提示词的委托到达；一旦该委托被移除，未被引用的最终审查模板将被孤立。）Integration 部分关于 `superpowers:requesting-code-review` 提供"审查者子代理的代码审查模板"的注释被更正为仅适用于最终审查。
- **示例工作流：** 示例中的质量审查者行更新为新的裁决词汇（"任务质量：已批准"）；最终审查者的"可以合并"行保留。
- 流程图拓扑不变；⚠️ 通道由控制器指导处理，不是新的图分支。

## 这不修复什么（已知，推迟）

规格审查者对照控制器粘贴的任务文本进行判断；它无法捕获控制器从计划中提取时丢弃的需求。这是"控制器提供完整文本"的架构属性，不是提示词问题，超出本范围。

## 验证

- 插件基础设施测试（`tests/`）仍然通过。
- 在变更前后运行 SDD 技能行为评估（`git submodule update --init evals`，然后按 `evals/README.md`）。具体：`sdd-go-fractals`、`sdd-svelte-todo`、`sdd-rejects-extra-features`（端到端 SDD，包括规格审查者的 YAGNI 门），以及 `spec-reviewer-catches-planted-flaws`。
- 此变更暴露的已知评估缺口：没有现有场景在单个 SDD 任务内植入代码质量缺陷并断言每任务质量审查者捕获它，也没有场景测量每审查者探索成本（工具调用/grep 计数）。添加一个覆盖第一个缺口的场景（植入的单任务质量缺陷 → 每任务审查者必须在最终审查前标记它）。对于探索成本，在前后评估记录中手动比较审查者子代理工具调用计数。
