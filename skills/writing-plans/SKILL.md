# 编写计划

## 概述

为一位没见过此代码库或此规格说明的工程师编写实现计划。假设他们一旦知道确切的接口和确切的测试，就能用项目语言写出符合惯例的代码，并且计划中留白之处他们会做出合理选择。他们无法知道的是你的决定：哪些文件、哪些名称和签名、规格中的哪些值、哪些测试证明每个任务。把这些记录下来。把完整计划拆成小任务交给他们。DRY。YAGNI。TDD。频繁提交。

**开始时声明：**"我正在使用 writing-plans 技能创建实现计划。"

**上下文：**如果在隔离的 worktree 中工作，该 worktree 应在执行时通过 `superpowers:using-git-worktrees` 技能创建。

**计划保存至：**`docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （用户对计划位置的偏好优先于此默认值）

## 范围检查

如果规格涵盖多个独立子系统，应在头脑风暴阶段拆分为子项目规格。若未拆分，建议拆成多个独立计划——每个子系统一个。每个计划都应能独立产出可运行、可测试的软件。

## 文件结构

在定义任务之前，先规划将创建或修改哪些文件，以及每个文件负责什么。分解决策在此确定。

- 设计边界清晰、接口明确的单元。每个文件应有单一明确职责。
- 你能同时放在上下文中思考的代码，推理效果最好；文件聚焦时，你的修改也更可靠。优先选择更小、更聚焦的文件，而非职责过多的大文件。
- 一起变更的文件应放在一起。按职责拆分，而非按技术分层。
- 在现有代码库中，遵循既有模式。如果代码库使用大文件，不要单方面重构——但如果你要修改的文件已变得臃肿，在计划中包含拆分是合理的。

此结构决定任务分解。每个任务应产出可独立理解的、自包含的变更。

## 任务粒度

任务是承载自身测试周期、且值得由新审查者把关的最小单元。划定任务边界时：将设置、配置、脚手架和文档步骤并入其交付物需要它们的任务；仅在审查者能有意义地拒绝一个任务而批准相邻任务之处拆分。每个任务以可独立测试的交付物结束。

## 步骤粒度

**每个步骤是一个动作，带可检查的结果：**
- "编写失败的测试" - 步骤
- "运行它，确认失败" - 步骤
- "实现最小代码使测试通过" - 步骤
- "运行测试，确认通过" - 步骤
- "提交" - 步骤

## 计划文档头部

**每个计划必须以以下头部开始：**

```markdown
# [功能名称] 实现计划

> **致智能体执行者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法跟踪。

**目标：** [一句话描述构建什么]

**架构：** [2-3 句话说明方法]

**技术栈：** [关键技术/库]

**规格：** [此计划实现的规格/设计文档路径——计划以规格为依据，因此规格随计划同行；执行者两者都读]

## 全局约束

[规格的项目级要求——版本下限、依赖限制、命名和文案规则、平台要求——每行一条，值从规格中逐字复制。每个任务的需求都隐含包含本节。]

## 审查重点

[规格暗示但没有任何任务的测试覆盖、且最可能让使用者踩坑的五类输入或失败模式——每行一条，写明输入或条件以及合理预期行为，最可能的在前。规格是愿景文档：它说明软件必须做什么，而非它将遇到的一切；它对某输入的沉默不代表该输入可以破坏程序。在此处一次性写下清单，对照规格。然后为每行添加测试，将其固定到拥有该代码的任务中，使用该任务自身的步骤风格。]

---
```

## 任务结构

````markdown
### 任务 N：[组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[此任务从先前任务使用的内容——确切签名]
- 产出：[后续任务依赖的内容——确切函数名、参数和返回类型。任务的实现者只看到自己的任务；此块是他们了解相邻任务所用名称和类型的方式。]

- [ ] **步骤 1：编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试，确认失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，报 "function not defined"

- [ ] **步骤 3：在 `exact/path/to/file.py` 中实现 `function(input: InputType) -> ResultType`**

当签名和测试留有选择空间时，用一行说明方法（调用哪个库、用哪种数据结构）；仅对无法由签名和测试确定的算法给出代码块。

- [ ] **步骤 4：运行测试，确认通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 步骤包含什么

当实现者能据此写出唯一合理的内容时，步骤即完成。这就是全部要求：无歧义，而非完整。每类步骤只携带使其无歧义所需的内容，不多不少：

- **测试步骤：**测试名称及其断言，以代码形式给出，包含规格中的确切值。
- **代码步骤：**确切签名（名称、参数、返回类型）、所在文件，以及规格固定的具体值。实现者编写函数体。仅当签名和测试无法确定算法，或规格固定了确切文案时，才给出函数体。
- **验证步骤：**要运行的命令，以及表示通过的结果。
- **引用另一任务：**该任务的接口块说明用什么；计划不重复该任务的代码。

计划是实现者无法独自做出的决定集合。计划比它描述的代码还长，说明它写了代码而非计划。不决定任何事的行（"TBD"、"处理边界情况"、"添加适当验证"、"为上述编写测试"、没有任务定义的类型或函数）是相反的失败，自审会同时捕捉两者。

## 自审

写完完整计划后，以全新视角对照规格检查计划。这是你自己运行的清单——不是派发子智能体。

**1. 规格覆盖：**浏览规格的每个章节/需求。你能指出实现它的任务吗？列出任何缺口。

**2. 步骤扫描：**每个步骤必须让实现者写出唯一合理的内容，且不得携带更多：不决定任何事的行是缺口，签名和测试已确定的函数体是转录。两者都要修正。

**3. 类型一致性：**后续任务中使用的类型、方法签名和属性名是否与先前任务定义的一致？任务 3 中叫 `clearLayers()`、任务 7 中叫 `clearFullLayers()` 的函数是 bug。

**4. 审查重点：**对规格暗示的每类输入或失败模式，是否有任务的测试覆盖它？最可能让使用者踩坑的五个未覆盖项放入审查重点章节，每行对应的测试添加到拥有该代码的任务。空章节意味着你检查过且未发现，而非你跳过了检查。

**5. 比例：**比较计划长度与规格长度。计划比它实现的规格长数倍，就是程序的转录，而非计划。如果代码块占文档大部分，用签名、测试名称和断言替换函数体，并检查每个步骤是否仍无歧义。

如发现问题，就地修正。无需重新审查——修正后继续。如发现规格需求无对应任务，添加该任务。

## 执行交接

保存并自审计划后，将链接发给人类伙伴阅读。如果他们已明确提供执行方法，请他们审查计划并确认其捕捉了他们的意图；实现前等待该审查，然后使用保留的方法。否则，请他们审查计划并在实现前选择执行方法。

**当尚未提供执行方法时：**

**"计划已完成并保存至 `docs/superpowers/plans/<filename>.md`。请审查计划。你更倾向哪种执行方式？**

- **子智能体驱动** - 新子智能体实现每个任务，新审查者在下一个任务开始前检查它，最后进行整分支审查。最彻底；每个任务和每次审查都消耗新上下文。
- **原生** - 我在本会话中亲自实现每个任务，按此 harness 的工作方式，然后由能力最强模型上的新审查者检查整个分支。最便宜最快；结束前无独立审查。与中档会话模型配合良好，因为计划承载设计。

**对此计划我推荐 <两者之一>，因为 <计划中的一句话：任务间接口依赖程度、任务数量、已发布错误的代价>。计划是否捕捉了你的意图，我们该用哪种方式？"**

**当已提供执行方法时：**

**"计划已完成并保存至 `docs/superpowers/plans/<filename>.md`。请审查计划。它是否捕捉了你的意图？"**

**若选择子智能体驱动：**
- **必需子技能：**使用 superpowers:subagent-driven-development

**若选择原生：**
- **必需子技能：**使用 superpowers:executing-plans
