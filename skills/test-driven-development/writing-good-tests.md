# 编写优质测试

**在以下情况加载本参考：** 编写或修改测试、添加 mock，或为测试添加清理/辅助方法时。

## 概述

测试存在的意义是捕获特定的故障。以下两条原则统领全文：

```
1. 每个测试都指明它所捕获的故障
2. 每个测试都针对真实对象进行验证
```

严格的 TDD 会自然产生这两点：先写测试并观察它在真实代码上失败，就已证明它能失败；只有当真实依赖确实缓慢或属于外部依赖时，才值得使用 mock。

## 原则 1：指明故障

在编写测试主体之前，先回答：**哪个生产代码变更应使此测试失败——该变更是 bug 还是有意决策？** 测试通过捕获错误分支、缺失的副作用、错误参数、边界情况或契约破坏来证明自身价值。

**独立推导期望值。** 使用字面量和手工核对的 fixture；带字面量 `want` 值的表驱动测试是首选形式。由被测代码或其辅助函数计算出的期望值，无论该代码做什么都会通过：

```typescript
// ❌ 镜像断言：同一个构建器计算两边——永远为真
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ 手工推导的字面量
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**不要做变更检测器。** 如果只有有意决策才能让测试失败——常量值、精确的消息措辞、私有结构——那么它会在重构时触发，却对 bug 无动于衷。应测试依赖于该决策的行为：不是 `expect(MAX_RETRIES).toBe(5)`，而是"失败的调用重试 5 次，第 6 次不再发生。"

**测行为，不测文本。** 断言脚本、skill 或配置包含某一行，只能证明源文件就是源文件。应针对受控输入运行脚本，并断言输出、副作用或退出码。指导 agent 的文档通过消费方 agent 的行为来测试（superpowers:writing-skills）；面向人类的散文根本不需要测试。

**测你的代码，不测框架。** 测试你的代码在边界处建立的契约——你注册的路由、你发出的查询、你产生的载荷。上游机制是维护者的测试职责（典型例子：断言你的路由器调用了已注册的处理器——那是框架的测试，不是你的）。当上游行为确实令你意外时，写一个窄范围的特征测试来指明该假设。同样的边界适用于你的代码内部：构造函数、getter、常量和平凡的转发，只有在它们执行校验、规范化、默认值、派生、约束或产生副作用时才值得测试——否则应断言依赖于它们的第一个消费者可见结果。

### 门控函数

```
在编写测试主体之前：
  指明会使此测试失败的生产代码变更。

  无法指明                → 围绕可观察行为重新设计
  "源文本变了"            → 运行产物并断言其效果
  只有有意决策            → 变更检测器；测试依赖于该决策的行为

  确认期望值的推导未使用被测代码。
  如果它复用了代码的逻辑或辅助函数：
    替换为字面量或手工核对的 fixture
```

## 原则 2：针对真实对象验证

**mock 本身不配任何断言。** mock 断言在 mock 存在时通过、缺失时失败——它对组件本身一无所知。应断言真实组件的行为；如果你检查的正是 mock，那就取消 mock 或删除该断言。

```typescript
// ✅ 真实行为
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ mock 存在性
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**你的搭档的纠正：**"我们是在测试 mock 的行为吗？"

**在正确的层级 mock。** 替换真实方法前，先了解它的每一个副作用；mock 掉缓慢或外部的操作，保留测试所依赖的部分为真实。不确定时，先针对真实实现运行测试，观察实际需要发生什么。

```typescript
// ❌ mock 吞掉了重复检测所读取的配置写入
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ 只 mock 缓慢的服务器启动；配置写入保持真实
vi.mock('MCPServerManager');
```

**让替身具体化。** 当参数、调用次数或顺序属于契约时，应断言它们——接受任何东西的假对象什么也验证不了。为每个分支（成功、错误、格式错误）提供各自的 fixture 或 spy，使错误分支无法满足期望。

**完整镜像真实数据。** 按现实中的完整结构 mock——所有已文档化的字段——而不只是测试读取的那些。当下游代码读取被省略的字段时，部分 mock 会静默失败：测试通过，集成却坏了。

**生产类只携带生产方法。** 只有测试需要的清理逻辑应放在测试工具中，绝不要作为生产类上的 `destroy()`。问自己：这个方法只从测试中调用吗？这个类拥有该资源的生命周期吗？答案是否定 → 放入测试工具。

**优先使用真实组件而非复杂 mock。** 当 mock 设置超出测试逻辑、mock 缺少真实组件拥有的方法，或 mock 变更导致测试失败时，改用真实组件的集成测试。**你的搭档的问题：**"我们这里真的需要用 mock 吗？"

### 门控函数

```
在添加 mock 或测试辅助之前：
  列出真实方法的副作用；保留测试所依赖的部分为真实——
  在其下层 mock 掉缓慢/外部的层级。

  mock 响应镜像完整的真实结构。

  只有测试调用的方法应放在测试工具中，而非生产代码。

  准备对 mock 本身断言？
    取消 mock 或删除该断言。
```

## 测试随实现一同交付

TDD 循环——失败测试、最小实现、重构——就是"完成"的含义。交付行为所需的测试，且仅交付这些：平凡代码和人类散文不需要测试，为满足流程而写的测试将永远付出维护成本。

## 变异检查

完成前，在脑中变异生产代码；每个现实的变异都应至少让一个测试失败：

- 错误的常量或参数
- 错误的分支处理器
- 缺失的状态变更或副作用
- 空或默认返回值
- 缺失对零、空、nil、未授权或格式错误输入的校验

没有任何测试捕获的变异，意味着该行为未受保护——或该测试是同义反复。

## 快速参考

| 当你…… | 做 |
|-------------|-----|
| 编写任何测试 | 指明它捕获的故障——是 bug，不是决策 |
| 构建期望值 | 手工推导；绝不用被测代码 |
| 测试脚本或文档 | 运行它 / 对其消费方施压测试；绝不 grep 其文本 |
| 想测试依赖 | 测你的边界契约，不是它们已文档化的机制 |
| 想对 mock 元素断言 | 测试真实组件，或取消 mock |
| 即将 mock 一个方法 | 了解其副作用；mock 缓慢/外部的层级 |
| 构建 mock 响应 | 完整镜像真实结构 |
| 需要仅测试使用的清理 | 放入测试工具 |
| 看到 mock 设置膨胀 | 改用真实组件的集成测试 |
| 完成测试文件 | 运行变异检查 |

## 警示信号

- 设置和断言共享同一对象，保证相等
- 测试只能通过 panic、崩溃或缺失选择器失败
- 测试在每次有意变更时失败，却从不因意外破坏而失败
- 期望值隐藏在循环、构建器或辅助函数背后
- 测试 grep 源文本，或断言已移除的符号保持移除
- 即使只剩框架，测试仍然有意义
- 测试为覆盖率而存在，不检查任何副作用或结果
- 断言检查 `*-mock` 测试 ID，或移除 mock 后失败
- 某方法只从测试文件中调用
- mock 设置超过测试的一半，或你无法解释为何需要该 mock
- "为了保险起见"而 mock
