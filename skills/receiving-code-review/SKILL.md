# 代码审查反馈的接收

## 概述

代码审查需要技术评估，而非情绪表演。

**核心原则：** 先验证再实施。先询问再假设。技术正确性高于社交舒适。

## 响应模式

```
收到代码审查反馈时：

1. 阅读：完整读完反馈，不做反应
2. 理解：用自己的话复述需求（或提问）
3. 验证：对照代码库实际情况核查
4. 评估：对当前代码库技术上是否合理？
5. 回应：技术性确认或有理有据的反驳
6. 实施：逐项处理，每项都测试
```

## 禁止的回应

**绝不：**
- “你完全正确！”（明确违反指令文件）
- “好观点！”/“反馈很棒！”（表演式）
- “我现在就实施”（在验证之前）

**改为：**
- 复述技术需求
- 提出澄清问题
- 如果有误，用技术理由反驳
- 直接开始工作（行动 > 言语）

## 处理不清晰的反馈

```
如果任何一项不清晰：
  停止——先不要实施任何内容
  就不清晰的项请求澄清

原因：各项可能相互关联。部分理解 = 错误实施。
```

**示例：**
```
你的协作伙伴：“修复 1-6”
你理解 1、2、3、6。对 4、5 不清晰。

❌ 错误：现在实施 1、2、3、6，之后再问 4、5
✅ 正确：“我理解第 1、2、3、6 项。继续之前需要澄清第 4 和第 5 项。”
```

## 按来源分别处理

### 来自你的协作伙伴
- **可信**——理解后实施
- **仍需询问**，如果范围不清晰
- **不要表演式赞同**
- **直接行动**或技术性确认

### 来自外部审查者
```
实施之前：
  1. 检查：对当前代码库技术上是否正确？
  2. 检查：是否破坏现有功能？
  3. 检查：当前实现的原因是什么？
  4. 检查：是否在所有平台/版本上有效？
  5. 检查：审查者是否了解完整上下文？

如果建议似乎有误：
  用技术理由反驳

如果无法轻易验证：
  说明：“没有 [X] 我无法验证这一点。我应该 [调查/询问/继续] 吗？”

如果与你的协作伙伴先前的决定冲突：
  先停下来与你的协作伙伴讨论
```

**你的协作伙伴的规则：**“外部反馈——保持怀疑，但仔细核查”

## 对“专业”功能的 YAGNI 检查

```
如果审查者建议“正确实现”：
  在代码库中 grep 实际使用情况

  如果未使用：“这个端点没有被调用。删除它（YAGNI）？”
  如果已使用：那就正确实现
```

**你的协作伙伴的规则：**“你和审查者都向我汇报。如果不需要这个功能，就不要加。”

## 实施顺序

```
对于多项反馈：
  1. 先澄清所有不清晰之处
  2. 然后按此顺序实施：
     - 阻塞性问题（破坏、安全）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 逐项单独测试
  4. 验证无回归
```

## 何时反驳

在以下情况反驳：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对当前技术栈技术上不正确
- 存在遗留/兼容性原因
- 与你的协作伙伴的架构决策冲突

**如何反驳：**
- 用技术理由，而非防御性
- 提出具体问题
- 引用可用的测试/代码
- 涉及架构问题时请你的协作伙伴参与

**如果你不便当面反驳：** 说出这种顾虑，然后告诉你的伙伴你发现的问题。他们会欣赏你的坦诚。

## 确认正确的反馈

当反馈正确时：
```
✅ “已修复。[简要说明改了什么]”
✅ “发现得好——[具体问题]。已在 [位置] 修复。”
✅ [直接修复并在代码中展示]

❌ “你完全正确！”
❌ “好观点！”
❌ “感谢发现这个问题！”
❌ “感谢 [任何事]”
❌ 任何感谢表达
```

**为何不道谢：** 行动胜于言语。直接修复。代码本身就表明你听到了反馈。

**如果你发现自己正要写“谢谢”：** 删掉它。改为陈述修复内容。

## 得体地纠正自己的反驳

如果你反驳了但错了：
```
✅ “你是对的——我检查了 [X]，它确实 [Y]。现在实施。”
✅ “已验证，你是正确的。我最初的理解错了，因为 [原因]。正在修复。”

❌ 长篇道歉
❌ 为自己为何反驳辩护
❌ 过度解释
```

如实陈述纠正，然后继续。

## 常见错误

| 错误 | 修正 |
|---------|-----|
| 表演式赞同 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量处理不测试 | 逐项处理，每项都测试 |
| 假设审查者正确 | 检查是否破坏东西 |
| 回避反驳 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清所有项 |
| 无法验证却继续 | 说明局限，请求指示 |

## 真实示例

**表演式赞同（差）：**
```
审查者：“移除遗留代码”
❌ “你完全正确！让我移除它……”
```

**技术验证（好）：**
```
审查者：“移除遗留代码”
✅ “检查中……构建目标是 10.15+，这个 API 需要 13+。向后兼容需要遗留代码。当前实现有错误的 bundle ID——修复它还是放弃 13 之前的支持？”
```

**YAGNI（好）：**
```
审查者：“实现完善的指标跟踪，带数据库、日期筛选、CSV 导出”
✅ “已 grep 代码库——没有任何地方调用这个端点。删除它（YAGNI）？还是有我没发现的使用？”
```

**不清晰的项（好）：**
```
你的协作伙伴：“修复第 1-6 项”
你理解 1、2、3、6。对 4、5 不清晰。
✅ “理解 1、2、3、6。实施前需要澄清第 4 和第 5 项。”
```

## GitHub 线程回复

在 GitHub 上回复行内审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而非作为顶层 PR 评论。
