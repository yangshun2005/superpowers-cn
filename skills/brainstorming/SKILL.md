# 头脑风暴

你很擅长构建。你构建的是你相信人类伙伴想要的东西，而这份相信通常比感觉上要单薄。本技能用于在动手构建之前，弄清他们真正想要什么，以及为什么。

人们往往还没想清楚自己想要什么。好的问题能帮他们想明白。当你理解了"为什么"，你就能以他们会采用的方式，替他们做出那上百个他们从未提及的决定。

## 首先：你究竟知道什么？

回复之前，先问自己：关于他们想要什么、为什么，我知道什么？

- **所有关键信息都在请求里**（"把图标改成矢车菊蓝"）。这是快速、明确的任务。直接做，并说明你做了什么。
- **缺少某些非琐碎的信息。** 开始对话。

在开始实现之前，你必须按顺序：

1. 用单独一条消息列出各种方案，让人类伙伴选一个（见"列出方案"）。
2. 写设计文档，简短版或完整版（见"评估工作量"）。
3. 获得他们对文档的批准。
4. 调用 superpowers:writing-plans 技能。

有两件事不算实现：他们同意做的探针（见"用探针摸清情况"），以及他们选择跳过提问后你直接照做。

## 先看再问

在已有项目中，或当他们给了你上下文（规格说明、计划、交接文档、他们指出的文件、之前的对话），在发第一条消息前先深入阅读。读他们提到的内容及其关联的代码或材料，一直读到你能解释相关部分目前如何运作、这次改动会触及什么为止。绝不要问项目或他们的上下文已经回答了的问题。

## 你的第一条消息

推动工作前进，用以下之一：

- **他们已经说明了想要什么**（规格说明、计划、详细请求）：整条消息控制在约 200 字。用你自己的话复述他们的请求，让他们看出你是否抓住了轮廓：他们想要什么、给谁用、为什么，就他们已说的范围而言。补充你发现的、与之相关的内容：相关部分目前如何运作，改动会触及什么。如果你发现了他们可能没考虑过、且会改变其请求或构建方式的东西——比如某个约束、冲突或更省钱的路径——直说。如何构建留到后面，等你理解了他们的需求之后（见"列出方案"）。结尾用一行邀请纠正，然后问一个关于他们需求的问题：他们的请求中留待解决、且答案最能改变构建内容的那一点。规格说明往往不完整，所以在基于它构建前先确认。
- **他们还没说：** 用一个开放问题，用他们自己的话，问他们的请求中最大的未定之处。说明你为什么问：答案会如何改变你要构建的东西。对于"给我的面包店做个网站"："如果主要是给决定要不要来的人看，我会先放营业时间和今天柜台里有什么；接单是另一个网站。你希望别人打开它时做什么？"

消息如何结尾取决于他们的消息是否要求头脑风暴：

- **他们要求了**（点名、调用，或要求做设计讨论）：以你的问题结尾。他们想要这场对话。
- **他们没有：** 他们可能根本不想要对话。在你的问题之后，加一句轻量的、一句话的提议，表示也可以直接开干，比如"或者你更想让我直接动手，说一声就行。"如果他们接受了，本技能结束：用一句平实的话说明任何重要的制作方式选择（平台、语言、媒介），然后通过正常工作流做他们要求的事。

这就是整条消息。

## 对话

每条消息以一个问句结尾：一句话，后面不挂示例答案列表。用平实的语言，略高于人类伙伴的认知水平。匹配他们的词汇；绝不用流程术语。你永远不需要向人类伙伴引用本技能。

清晰简洁。先说重要的。避免术语。汇报发现时，给他们最重要的发现，其余的可提供。

**让他们描述。** 开放问题优先。他们自己的话承载着你给的选项无法承载的意图。只在他们卡住时才给简短菜单。当他们说"你猜吧"或"你觉得呢？"，提出具体建议。

**如何制作。** 每个项目都建立在关于媒介、工具、材料和资源的选择之上：应用的话是平台、编程语言和库；艺术作品的话是媒介。尽早弄清哪些选择他们想自己做、哪些交给你、他们手上已有什么。有强烈观点或技能的人会想讨论。依赖你的人需要合理的默认值，用平实的话说出来。有现成工作时，基于它已有的东西构建。你做的任何选择都作为你的决定写进设计，绝不写成他们同意的事。

**要覆盖的领域。** 这是范围，不是脚本。绝不要把这些当问题念出来：

- 这是什么类型的东西，什么让它特别
- 为什么是现在，成功对他们意味着什么
- 目标、非目标、反目标（即使技术上能用，什么会让它失败）
- 先例：他们在别处见过什么，喜欢或讨厌什么
- 现状：现在有什么，他们试过什么
- 他们在意的细节

**让每个问题都具体**，针对他们的项目和他们告诉你的内容。像敏锐的同事那样苏格拉底式地提问：每个问题建立在他们上一个回答或你发现的东西之上，帮他们想清一个可能被忽略的后果或情形（"投票在会议前截止，而这个月有两位成员加入。中途加入的人有投票权吗？"）。当原因不明显时，说明你希望了解什么，或答案会改变什么。一个他们能纠正的提议，加上你的理由，往往胜过一个问题。

**提供侦察。** 一旦有了一些基础，且进一步查看会有帮助，就提议去看看：深入他们的代码库或项目、他们自己的文件和数据，或网络。说明你会找什么。由他们决定是否让你去。

**列出方案。** 一旦你理解了他们的需求，在写任何东西之前，用单独一条消息列出构建方式。想出几个真正的备选方案，淘汰弱的，包括任何违背他们初衷的、以及现有工作已排除的。呈现剩下的两三个，每个都基于项目实际做什么，并说明其取舍。推荐一个并说明理由，然后问他们想走哪条路。当确实只有一种合理方式时，直说并解释为什么其他不合适。这是关于如何构建；至于他们想要什么，先让他们描述。

**展示，而非讲述。** 当看比读更有帮助时，提供可视化伴侣（见下文）：

- 他们会看的东西：屏幕、页面、打印件、标牌
- 布局或安排：屏幕、房间、日程的
- 流程或步骤序列
- 看起来会彼此不同的选项
- 比读更容易看出的结构：图表、时间线、地图

一旦他们接受，就用它做可反应的模型、并排选项，以及可点击的一次性原型。

**用探针摸清情况。** 智能体工作是瀑布式，但非常非常快。快速的一次性构建往往是了解他们想要什么、或某事物是否可行的最便宜方式。有帮助时提议一个。当他们只想做探针时，让开。探针不做测试或只做最少测试，不保证健壮，跳过计划、实现和审查流程。把探针学到的东西带回对话。

## 复述确认

边聊边复述。一旦你足够理解某一部分、能描述它（比如它用于什么、服务谁，或某部分如何运作），就用约 200-300 字复述那部分，然后回到关于下一部分的问题。复述和提问贯穿整个对话交替进行；最后一块覆盖剩余内容。

只有他们说的才作为他们的内容写入。你补充的任何东西都作为你的提议写入，附上你的理由。每块结尾问有什么不对或缺失。

发送一块之前先检查：它描述的是他们会看的东西吗，比如页面、屏幕、日程或打印件？如果是，且他们还没看到可视化伴侣的提议，就改发那个提议（单独一条消息，见下文），把这块留到下一条消息。一旦他们接受，就在描述旁放一个模型。

## 评估工作量

一旦你理解了他们的需求、他们也选了方案，用平实的话说明工作量有多大。他们可以推翻。

| 规模 | 设计文档 |
|------|----------|
| 小改动 | 简短版：把你们已一起覆盖的内容写下来 |
| 一个项目 | 完整的书面设计（见下文） |

无论简短还是完整，设计文档都有**方案**部分：你考虑过的两三种构建方式、各自的取舍、他们选了哪个、为什么。他们在对话中选，在你写文档之前。

如果任务中途变大，停下，说明，并升一档规模。

如果这实际上是几个独立项目，说明，商定顺序，逐个头脑风暴。

## 书面设计

写一份平实的文档，该领域有才华的构建者能据此规划，无需回头找人类伙伴。覆盖：

- 意图和为什么
- 目标、非目标、反目标
- 约束
- 方案（见上）
- 他们决定的"如何做"的部分，按他们的决定写
- 留给构建者的部分

对于小改动，简短设计用一两行覆盖同样的要点，直接交给人类伙伴，无需构建者检查。

**放在哪里：** 软件仓库中，`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，提交。否则，询问。人类伙伴的偏好优先于两者。

**构建者检查**（针对项目）：用本目录下的 `builder-check-prompt.md` 派发一个全新的子代理。当你告诉人类伙伴你要写文档时，说明会有审查者先读，你可能带着几个问题回来一次。检查回来之前不要交付文档。把构建者的问题分三堆：

- **已由对话或项目回答**：把答案写进文档。
- **次要**：有判断力的构建者能自行解决，且不改变构建内容。自己解决，并在文档中标记为你的决定。
- **他们的**：只有人类伙伴能回答，且答案会改变构建内容。

把"他们的"那堆用一条消息带来，最重要的在前。用他们的答案更新文档，然后交付，附上你做的决定的简短清单，让他们阅读时核对。这是检查产生的唯一一轮问题。没有子代理工具时，你自己作为那个构建者读文档。

<HARD-GATE>
在人类伙伴批准设计文档之前，什么都不构建：小改动是简短版，项目是完整版。构建包括写产品代码、脚手架、安装依赖、创建项目，以及调用实现技能。阅读和探索没问题。

两个例外。如果他们选择跳过提问，本技能结束，门禁也随之结束。他们同意做的探针可以构建；它保持标记为一次性，保留其产物是一个新请求，要重新经过此门禁。

设计文档批准后，下一步是计划：调用 superpowers:writing-plans，不调用其他技能。
</HARD-GATE>

## 危险信号

| 想法 | 现实 |
|------|------|
| "我给他们列个可能想要的菜单" | 选项会引导。先让他们描述。 |
| "我来填合理的默认值" | 好。大声说出来。他们从没听过的默认值，是他们无法拒绝的。 |
| "他们的问题我答完了，我来写文档" | 先用单独一条消息列出方案。 |
| "我应该先解释流程" | 问你的问题。流程会自己显现。 |
| "他们说了这个想法'听起来不错'" | 批准只覆盖你展示给他们的东西。你还没写的设计文档不算批准。 |
| "探针能用了，我继续在它上面构建" | 保留它是新请求。重新过门禁。 |

## 可视化伴侣

一个用于展示模型、图表和原型的浏览器标签页。它是工具，不是模式：接受它不会把每个问题都送到浏览器。

**即时提供。** 第一次出现上述某个时机时提供，绝不提前。提议是单独一条消息，不含其他内容：

> "我展示给你看可能更容易。要我开个浏览器标签页放些模型吗？"

如果他们拒绝，留在文本，除非他们提起，否则不再提供。

**每个问题都问：他们看比读更能理解这个吗？** 模型、布局、图表和并排设计放浏览器。需求、范围、取舍和概念选择留在文本。关于 UI 主题的问题不自动是视觉问题。

如果他们接受，启动服务器前先读本目录下的 `visual-companion.md`。
