# 完成开发分支

## 概述

**核心原则：** 验证测试 → 检测环境 → 呈现选项 → 执行选择 → 清理。

**开始时声明：** “我正在使用 finishing-a-development-branch 技能来完成这项工作。”

## 第 1 步：验证测试

运行项目的完整测试套件（`npm test` / `cargo test` / `pytest` / `go test ./...`）。

**如果测试失败**，报告失败并停止——菜单只在测试全部通过后出现：

```
测试失败（<N> 个失败）。完成前必须修复：

[显示失败]
```

**如果测试通过：** 继续第 2 步。

## 第 2 步：检测环境

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# 趁仍在工作区内时捕获——第 5 步会切换目录，
# 而清理（第 6 步）需要这个值
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

这决定了显示哪个菜单以及清理方式：

| 状态 | 菜单 | 清理 |
|-------|------|---------|
| `GIT_DIR == GIT_COMMON`（普通仓库） | 标准 3 个选项 | 无工作树需清理 |
| `GIT_DIR != GIT_COMMON`，命名分支 | 标准 3 个选项 | 基于来源（见第 6 步） |
| `GIT_DIR != GIT_COMMON`，分离 HEAD | 精简 2 个选项（无合并） | 外部管理——保持原样 |

## 第 3 步：确定基础分支

基础分支是这项工作 Fork 出来的分支——通常在计划、对话或分支的上游中指明。如果尚不清楚，询问：“这个分支从 <你的最佳猜测> 分出——对吗？”合并前确认：合并到错误的基础分支代价高昂，难以撤销。

## 第 4 步：呈现选项

**普通仓库和命名分支工作树——仅呈现以下 3 个选项：**

```
实现完成。你想怎么做？

1. 本地合并回 <base-branch>
2. 推送并创建 Pull Request
3. 保持分支原样（我稍后处理）

选哪个？
```

**分离 HEAD——仅呈现以下 2 个选项：**

```
实现完成。你处于分离 HEAD 状态（外部管理工作区）。

1. 作为新分支推送并创建 Pull Request
2. 保持原样（我稍后处理）

选哪个？
```

严格按所写内容呈现菜单——简洁，每个选项都来自上述列表。丢弃工作仅在人类伙伴明确要求时发生（见下文“如果人类伙伴要求丢弃工作”）。等待他们的回答；集成决策由他们做出。

## 第 5 步：执行选择

### 选项 1：本地合并

```bash
# 获取主仓库根目录以保证 CWD 安全
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# 先合并——移除任何内容前验证成功
git checkout <base-branch>
git pull
git merge <feature-branch>

# 在合并结果上验证测试
<test command>
```

如果合并结果测试失败：停止，保持工作树和分支原样，并调查——尚未推送任何内容，因此合并是本地且可恢复的。

一旦合并结果通过：清理工作树（第 6 步），然后删除分支：

```bash
git branch -d <feature-branch>
```

### 选项 2：推送并创建 PR

```bash
git push -u origin <feature-branch>
# 从分离 HEAD 推送时，在远程命名新分支：
# git push origin HEAD:refs/heads/<new-branch>
```

然后使用托管平台的工具针对 <base-branch> 创建拉取/合并请求——如有 CLI 则用其 CLI，或用大多数托管平台在推送时打印的创建 URL——遵循仓库的 PR 模板和约定（如有），并向人类伙伴报告 URL。

保留工作树——人类伙伴在那里迭代 PR 反馈。

### 选项 3：保持原样

报告：“保留分支 <name>。工作树保留在 <path>。”

### 如果人类伙伴要求丢弃工作

此路径仅作为对明确要求丢弃工作的响应而存在。先确认：

```
这将永久删除：
- 分支 <name>
- 所有提交：<commit-list>
- 工作树位于 <path>

输入 'discard' 确认。
```

等待该确切确认。收到后：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

然后清理工作树（第 6 步）并强制删除分支：

```bash
git branch -D <feature-branch>
```

## 第 6 步：清理工作区

**适用于选项 1 和已确认的丢弃。** 选项 2 和 3 始终保留工作树。两个调用方都已切换到主仓库根目录——工作树移除必须在工作树之外运行——并使用第 2 步捕获的 `GIT_DIR`/`GIT_COMMON`/`WORKTREE_PATH` 值，这些值来自目录切换之前。

**如果 `GIT_DIR == GIT_COMMON`：** 普通仓库，无工作树需清理。完成。

**如果 `WORKTREE_PATH` 位于 `.worktrees/` 或 `worktrees/` 下：** Superpowers 创建了此工作树——我们负责清理：

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # 自愈：清理任何过期的注册
```

**如果移除被拒绝**（`contains modified or untracked files`）：工作树包含其他地方不存在的文件——未提交的计划、笔记或草稿。绝不要自行决定使用 `--force`。向人类伙伴展示利害关系并询问：

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
工作树移除被拒绝——这些文件从未提交：

<file list>

1. 清理前将它们提交到 <branch>
2. 将它们移动到 <main repo root>
3. 删除它们（不可恢复）

选哪个？
```

执行选择，然后移除工作树。

**否则：** 宿主环境拥有此工作区——保持原样。如果你的平台提供工作区退出工具，使用它。

## 快速参考

| 选项 | 合并 | 推送 | 保留工作树 | 清理分支 |
|--------|-------|------|---------------|----------------|
| 1. 本地合并 | 是 | - | - | 是 |
| 2. 创建 PR | - | 是 | 是 | - |
| 3. 保持原样 | - | - | 是 | - |
| 丢弃（仅明确要求） | - | - | - | 是（强制） |

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| “本次会话早些时候测试通过了” | 在即将集成的树上运行测试套件。一次通过只证明它运行的那棵树。 |
| “他们显然想合并” | 集成是人类伙伴的决定。呈现菜单并等待。 |
| “他们似乎对这个功能做完了——我来提议丢弃它” | 菜单按所写内容即为完整。丢弃仅在人类伙伴明确要求时发生。 |
| “‘是的，删掉它’算作确认” | 只有输入 `discard` 一词才授权删除。 |
| “PR 已提交，工作树现在是杂物” | PR 反馈在该工作树中修复。它保留到工作落地。 |
| “这个其他工作树看起来过时了——我也清理一下” | 只清理 `.worktrees/` 或 `worktrees/` 下的工作树。其他一切属于宿主。 |
| “移除被拒绝——`--force` 只是完成清理” | 拒绝意味着文件仅存在于该工作树中。`--force` 会永久销毁它们。向人类伙伴展示并询问。 |
| “合并结果的失败可能是偶发的” | 合并结果失败会停止一切。调查时分支和工作树保持原样。 |
| “基础分支显然是 main” | 确认 Fork 点或询问。合并到错误的基础分支代价高昂，难以撤销。 |
| “推送被拒绝——强制推送能解决” | 推送被拒绝意味着远程已移动。调查；仅在人类伙伴明确要求时强制推送。 |
