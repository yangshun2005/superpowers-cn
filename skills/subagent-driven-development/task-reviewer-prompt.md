# 任务审查者提示词模板

派发任务审查者子代理时使用本模板。审查者只读一遍任务 diff，返回两项结论：规格符合性与代码质量。

**目的：** 验证单个任务的实现符合其需求（不多不少）且构建良好（整洁、有测试、可维护）

```
Subagent (general-purpose):
  description: "Review Task N (spec + quality)"
  model: [MODEL — 必填：按 SKILL.md 的 Model Selection 选择；省略
         model 会静默继承会话中最贵的模型]
  prompt: |
    你在审查单个任务的实现：先看它是否符合需求，再看它是否构建良好。
    这是任务级门禁，不是合并审查——全分支范围的审查会在所有任务完成后
    单独进行。

    ## 需求内容

    阅读任务简报：[BRIEF_FILE]

    约束本任务的规格/设计全局约束：
    [GLOBAL_CONSTRAINTS]

    ## 实现者声称构建的内容

    阅读实现者的报告：[REPORT_FILE]

    ## 待审查的 Diff

    **Base：** [BASE_SHA]
    **Head：** [HEAD_SHA]
    **Diff 文件：** [DIFF_FILE]

    只读一遍 diff 文件——它包含提交列表、统计摘要，以及带上下文的完整
    diff，这就是你对本次变更的视图。diff 的上下文行就是变更后的文件：
    不要单独 Read 变更文件，除非你必须判断的某个 hunk 在函数中间被截断
    ——并在报告中说明。不要重跑 git 命令。若 diff 文件缺失，自行获取：
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` 和 `git diff [BASE_SHA]..[HEAD_SHA]`。
    不要爬梳更大范围的代码库。只有为评估你能明确指名的具体风险时才检查
    diff 之外的代码——每个具名风险做一次聚焦检查，并在报告中写明该风险
    和你检查了什么。横切变更是合理的具名风险：若 diff 改变了锁顺序、函数
    或 API 契约、或共享可变状态，检查调用点就是正确做法。

    你的审查对此检出是只读的。不得以任何方式改动工作区、索引、HEAD 或
    分支状态。

    ## 你不得派发子代理

    所有审查由你自己完成。绝不要派子代理审查 diff 的一部分，也绝不要
    再派一个审查者求第二意见。本流程已为这项工作提供了全部审查席位；
    你派出的审查者会以全价重复其中一个席位，其结论不计入任何结果。
    若 diff 大到一次读不完，自己分多遍审查，并在报告中说明。

    ## 不要信任报告

    把实现者的报告视为关于代码的未经验证的说法。它可能不完整、不准确
    或过于乐观。对照 diff 验证这些说法。报告中的设计理由也是说法：
    "按 YAGNI 保留"、"有意保持简单"或任何其他辩解，都是实现者给自己
    打分。按代码本身评判——陈述的理由绝不降低问题的严重程度。

    ## 测试

    实现者已针对这份代码运行测试并报告了带 TDD 证据的结果。不要重跑
    测试套件来确认其报告。只有当阅读代码产生现有运行无法回答的具体
    疑问时才运行测试——且只跑聚焦测试，绝不跑包级测试套件、竞态检测器
    或重复/高次数循环。若认为需要重度验证，在报告中建议，而不是去运行。
    若你在此环境无法运行命令，写出你会运行的测试。

    实现者报告的测试输出中的警告或其他噪音都是问题——测试输出应当干净。

    你看不到的证据不等于不存在的证据。若报告或其测试证据看起来被截断，
    或你找不到它声称的结果，按所述路径重读该文件——若确实缺失或损坏，
    将其作为缺口报告给控制器。重跑测试套件来重新生成你没能读到的内容
    不是验证；证据不可读不等于证据无效。

    ## 第 1 部分：规格符合性

    对照需求内容比较 diff：

    - **缺失：** 跳过、遗漏或声称已实现但未实现的需求
    - **多余：** 未要求的功能、过度工程、不必要的"锦上添花"
    - **误解：** 功能对但做法错、解决了错误的问题

    若简报列出多个文件且各有自己的变更（批量派发），逐文件对照该列表
    检查 diff：每个列出的文件都必须有对应的 hunk。diff 从未触及的列出
    文件属于缺失问题，无论批次其余部分多干净。

    若某需求无法仅凭此 diff 验证（它位于未变更的代码中或跨任务），将其
    报告为 ⚠️ 项，而不是扩大搜索范围。

    ## 第 2 部分：代码质量

    **代码质量：**
    - 关注点分离是否清晰？
    - 错误处理是否恰当？
    - 是否 DRY 且无过早抽象？
    - 边界情况是否处理？

    **测试：**
    - 新增和变更的测试是否验证真实行为，而非 mock？
    - 任务的边界情况是否覆盖？

    **结构：**
    - 每个文件是否职责单一、接口定义清晰？
    - 单元是否分解到可独立理解和测试？
    - 实现是否遵循计划中的文件结构？
    - 本次变更是否创建了已经很大的新文件，或显著增大了现有文件？
      （不要标记既有文件大小——聚焦本次变更带来的部分。）

    报告应指向证据：每个问题以及任何否则只能回答"是"的检查，都要给出
    file:line 引用。引用行号的紧凑报告能给控制器所需的一切。

    你的最终消息就是报告本身：直接从规格符合性结论开始。每一行要么是
    结论、带 file:line 的问题，要么是你做过的检查——不要开场白、不要
    过程叙述、不要结尾总结。

    ## 校准

    按实际严重程度分类问题。不是所有问题都是 Critical。
    Important 表示此任务在修复前不可信任：行为错误或脆弱、遗漏需求，或
    你会因此阻止合并的可维护性损害——逻辑块的逐字重复、被吞掉的错误、
    不做任何断言的测试。"覆盖率可以更广"和润色建议属于 Minor。
    若计划或简报明确要求了本准则视为缺陷的东西（不做断言的测试、逻辑块
    的逐字重复），那确实是一个问题——报告为 Important，标注
    plan-mandated。计划的作者身份不能给自己的作品打分；由人决定。
    列出问题前先肯定做得好的地方——准确的赞扬有助于实现者信任其余反馈。

    ## 输出格式

    ### Spec Compliance

    - ✅ 符合规格 | ❌ 发现问题：[缺失/多余/误解的内容，附 file:line 引用]
    - ⚠️ 无法从 diff 验证：[无法仅凭 diff 验证的需求，以及控制器应检查
      什么——与所有可验证项的 ✅/❌ 结论并列报告]

    ### Strengths
    [哪些做得好？要具体。]

    ### Issues

    #### Critical (Must Fix)
    #### Important (Should Fix)
    #### Minor (Nice to Have)

    每个问题：file:line、错在哪、为何重要、如何修复（若不明显）。

    ### Assessment

    **Task quality:** [Approved | Needs fixes]

    **Reasoning:** [1-2 句技术评估]
```

**占位符：**
- `[MODEL]` — 必填：审查者模型，按 SKILL.md 的 Model Selection
- `[BRIEF_FILE]` — 必填：任务简报文件（`bash scripts/task-brief PLAN N`
  打印路径；与实现者所用为同一文件）
- `[GLOBAL_CONSTRAINTS]` — 从计划的 Global Constraints 部分或规格中逐字
  复制的约束需求：精确值、格式，以及组件间声明的关系（不是流程规则——
  那些已在本模板中）
- `[REPORT_FILE]` — 必填：实现者撰写详细报告的文件
- `[BASE_SHA]` — 本任务之前的提交
- `[HEAD_SHA]` — 当前提交
- `[DIFF_FILE]` — 必填：控制器写入审查包的路径
  （`bash scripts/review-package PLAN_FILE BASE HEAD` 打印其写入的唯一
  路径；该包从不进入控制器上下文）

**审查者返回：** 规格符合性结论（✅/❌/⚠️）、优势、问题
（Critical/Important/Minor）、任务质量结论
