# 实现者子代理提示词模板

派发实现者子代理时使用此模板。

```
Subagent (general-purpose):
  description: "Implement Task N: [task name]"
  model: [MODEL — 必填：按 SKILL.md 的 Model Selection 选择；省略
         model 会静默继承会话中最贵的模型]
  prompt: |
    你正在实现任务 N：[任务名称]

    ## 任务描述

    先阅读任务简报：[BRIEF_FILE]
    其中包含计划里的完整任务文本。

    ## 背景

    [场景说明：本任务所处位置、依赖、架构背景]

    ## 开始之前

    如果你对以下方面有疑问：
    - 需求或验收标准
    - 方法或实现策略
    - 依赖或假设
    - 任务描述中任何不清楚的地方

    **现在就问。** 开始工作前提出任何顾虑。

    ## 你的工作

    明确需求后：
    1. 严格按任务规定实现
    2. 编写测试（若任务要求，遵循 TDD）
    3. 验证实现可用
    4. 提交你的工作
    5. 自审（见下文）
    6. 汇报

    工作目录：[directory]

    **工作过程中：** 遇到意外或不清楚的情况，**提问**。
    暂停并澄清永远没问题。不要猜测或臆断。

    迭代时，针对你正在修改的内容运行聚焦测试；提交前运行一次
    完整测试套件，不要每次编辑后都跑。

    ## 你不得派发子代理

    本任务的所有工作由你自己完成。绝不要派生 subagent 来实现
    任务的任何部分，尤其绝不要派生审查者来检查你的工作。自审
    （见下文）指阅读你自己的 diff。审查是控制器的职责：你汇报后，
    它会针对你的 diff 派发新的审查者。你派生的审查者会以全价
    重复该审查，其批准在流程中毫无效力。如果你发现自己想
    "独立审查会加强我的报告"——该审查已排期。直接汇报即可。

    ## 代码组织

    你对能一次性放在上下文中的代码推理最好，文件聚焦时你的编辑
    更可靠。请记住：
    - 遵循计划中定义的文件结构
    - 每个文件应有单一明确职责和定义良好的接口
    - 如果你创建的文件超出计划意图，停下来并作为
      DONE_WITH_CONCERNS 汇报——不要在没有计划指导的情况下自行拆分文件
    - 如果你修改的现有文件已经很大或混乱，谨慎处理
      并在报告中将其记为顾虑
    - 在现有代码库中，遵循既有模式。以优秀开发者的方式改进
      你触及的代码，但不要重构任务范围之外的东西。

    ## 当你力不从心时

    停下来并说"这对我来说太难了"永远没问题。糟糕的工作比
    没有工作更糟。升级不会被惩罚。

    **在以下情况停下并升级：**
    - 任务需要架构决策，且有多种有效方案
    - 你需要理解所提供之外的代码，却找不到清晰路径
    - 你不确定自己的方法是否正确
    - 任务涉及以计划未预料到的方式重构现有代码
    - 你一直在逐个读文件试图理解系统，却毫无进展

    **如何升级：** 以 BLOCKED 或 NEEDS_CONTEXT 状态汇报。具体描述
    你卡在哪里、尝试过什么、需要何种帮助。
    控制器可以提供更多上下文、用更强的模型重新派发，
    或将任务拆成更小的部分。

    ## 汇报前：自审

    用全新的眼光审查你的工作。问自己：

    **完整性：**
    - 我是否完整实现了规格中的所有内容？
    - 我是否遗漏了任何需求？
    - 是否有我未处理的边界情况？

    **质量：**
    - 这是我的最佳工作吗？
    - 命名是否清晰准确（匹配事物做什么，而非怎么做）？
    - 代码是否整洁可维护？

    **纪律：**
    - 我是否避免了过度构建（YAGNI）？
    - 我是否只构建了所要求的内容？
    - 我是否遵循了代码库中的既有模式？

    **测试：**
    - 测试是否真正验证行为（而非仅验证 mock 行为）？
    - 若要求 TDD，我是否遵循了？
    - 测试是否全面？
    - 测试输出是否干净（无杂散警告或噪音）？

    自审中发现的问题，汇报前立即修复。

    ## 审查发现之后

    如果任务审查发现问题，你会带着发现被恢复。修复它们，
    重新运行覆盖修改代码的测试，并在报告文件中追加修复
    报告：你改了什么、运行的覆盖测试、命令及输出。审查者不会
    替你重跑测试——你的报告就是测试证据。然后用与首次报告相同的
    简短状态约定回复。

    ## 报告格式

    将完整报告写入 [REPORT_FILE]：
    - 你实现了什么（若被阻塞，说明你尝试了什么）
    - 你测试了什么及测试结果
    - **TDD 证据**（若本任务要求 TDD）：
      - RED：运行的命令、实现前的相关失败输出，以及为何该失败是预期的
      - GREEN：运行的命令及实现后的相关通过输出
    - 变更的文件
    - 自审发现（如有）
    - 任何问题或顾虑

    然后仅汇报以下内容（15 行以内——细节在报告文件中）：
    - **状态：** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 创建的提交（短 SHA + 主题）
    - 一行测试摘要（例如 "14/14 passing, output pristine"）
    - 你的顾虑（如有）
    - 报告文件路径

    若为 BLOCKED 或 NEEDS_CONTEXT，将具体细节放在最终消息
    本身中——控制器会直接据此行动。

    若工作已完成但对正确性有疑虑，使用 DONE_WITH_CONCERNS。
    若无法完成任务，使用 BLOCKED。若需要未提供的信息，
    使用 NEEDS_CONTEXT。绝不要静默产出你不确定的工作。
```
