# 让技能抵御合理化

属于 superpowers:writing-skills 的一部分。当基线失败是纪律性失败时使用：智能体知道规则，但在压力下跳过它。

## 让技能抵御合理化

执行纪律的技能（如 TDD）需要抵御合理化。智能体很聪明，在压力下会找漏洞。

**适用范围：** 本工具包针对纪律性失败——智能体知道规则，但在压力下跳过它。对于输出形态错误或遗漏元素，基于禁止的加固会适得其反；请改用 Match the Form to the Failure 中的形式。

**心理学说明：** 理解说服技巧为何有效，有助于系统性地应用它们。关于权威、承诺、稀缺、社会认同和统一原则的研究基础（Cialdini, 2021; Meincke et al., 2025），见本目录下的 persuasion-principles.md。

### 明确堵住每一个漏洞

不要只陈述规则——禁止具体的变通做法：

<Bad>
```markdown
先写代码后写测试？删掉。
```
</Bad>

<Good>
```markdown
先写代码后写测试？删掉。重新开始。

**没有例外：**
- 不要把它留作"参考"
- 不要在写测试时"改造"它
- 不要看它
- 删掉就是删掉
```
</Good>

### 应对"精神 vs 字面"的争论

尽早加入基础原则：

```markdown
**违反规则的字面就是违反规则的精神。**
```

这能切断整类"我在遵循精神"的合理化。

### 建立合理化对照表

从基线测试中收集合理化（见下文测试部分）。智能体找的每个借口都放进表里：

```markdown
| 借口 | 现实 |
|--------|---------|
| "太简单不用测" | 简单代码也会出错。测试只需 30 秒。 |
| "我之后测" | 测试立即通过证明不了任何东西。 |
| "后测能达到同样目标" | 后测 = "这段代码做什么？" 先测 = "这段代码应该做什么？" |
```

### 创建红旗清单

让智能体在合理化时容易自查：

```markdown
## 红旗 - 停下并重新开始

- 先写代码后写测试
- "我已经手动测过了"
- "后测能达到同样目的"
- "重要的是精神不是仪式"
- "这次不一样因为……"

**所有这些都意味着：删掉代码。用 TDD 重新开始。**
```

### 为违规症状更新 SDO

在描述中加入即将违规时的症状：

```yaml
description: 在实现任何功能或修复 bug 时使用，在编写实现代码之前
```
